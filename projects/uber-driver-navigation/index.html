Reframed Problem

This is an interruption-timing problem, not just a card-size problem.

Back-to-back trips are valuable. The interruption timing needs more context.

Product framing

When is it safe and useful to interrupt a driver?

Back-to-back value

Back-to-back trips support driver earnings and marketplace efficiency.

Where the risk appears

The same request UI can become risky when it surfaces during a maneuver-critical moment.

Design principle

Navigation should stay primary while the vehicle is moving.

Direction

Change request presentation based on speed, maneuver risk, and driver state.

Why It Matters

One prompt can affect safety, trust, and marketplace flow.

Safety

Visual distraction during high-attention driving moments.

Driver experience

Stress, annoyance, missed turns, and decision pressure.

Rider experience

Rerouting, longer ETA, and reduced trust.

Marketplace

Acceptance rate, request timeout, driver earnings, and rider wait time.

Root Cause Analysis

Four product conditions create the risk.

Timing conflict

01

Requests can arrive during exits, merges, turns, or dense intersections when route attention is highest.

Visual hierarchy conflict

02

Navigation is primary, but the request card can become the dominant layer at the wrong moment.

Decision pressure

03

Exclusive requests create timer pressure while the driver should still be focused on the current trip.

Market-density mismatch

04

Highway and dense-city contexts create different risks, but the same request UI can treat them too similarly.

What I Would Not Do

Some obvious fixes solve the wrong layer of the problem.

Judgment 01

I would not remove back-to-back requests because they support driver earnings and marketplace liquidity.

Judgment 02

I would not simply make the card smaller because the core issue is timing and attention demand.

Judgment 03

I would not rely only on a driver setting because safety-sensitive defaults should work without configuration.

Judgment 04

I would not use audio as the only solution because rider presence, noise, and language localization make it inconsistent.

Solution Alternatives

Several tactics help, but one system direction stands out.

The goal is not to remove requests. It is to change how they surface in risky moments.

Product-builder reasoning

I would start with a rule-based MVP instead of a heavy ML model because the first goal is to prove that presentation changes reduce route deviations near request events. Once the team validates the signal, the policy can evolve into a more personalized or predictive model.

The system should avoid hiding requests so often that drivers lose trust.
Any timer pause must avoid creating unfair marketplace delays.
Thresholds should differ by market, road type, and driver state.

PM Thinking

The right framing is interruption management, not cosmetic cleanup.

This is a product policy problem before it is a visual design problem.

Product framing

Back-to-back requests are valuable. The better move is not to remove them, but to redesign when and how the product asks for attention.

Safety vs marketplace speed

A small matching delay is acceptable if it lowers unsafe interaction during route-critical moments.

Information richness vs glanceability

Show less while moving. Restore richer detail when the driver is stopped or clear of the maneuver.

Default safety vs driver control

A future Focus Mode can help, but safer interruption handling should come from defaults first.

Global consistency vs local tuning

Use one interaction model globally, then tune thresholds by market context.

Product Builder Thinking

Roll it out in phases, then tune the policy.

The first goal is not perfect intelligence. It is a reliable policy with measurable behavior change.

Phase 01

Instrument request display events near maneuver windows.

Phase 02

Test compact moving-state banner against the current full card.

Phase 03

Add maneuver shielding for high-risk moments.

Phase 04

Pause or extend the acceptance timer for exclusive requests during maneuver windows.

Phase 05

Tune thresholds by market, road type, and driver behavior.

Small systems view

State inputs

Speed, maneuver proximity, road type, and request urgency.

Display policy

Choose full card, compact card, banner, audio summary, or queued state.

Measurement

Track display mode, route deviation, interaction while moving, and marketplace impact.

Final Takeaway

Dispatch should adapt to the driver's attention state, not compete with it.

The strongest driver experience is not the one that shows the most information fastest. It is the one that understands when the driver can safely process it.
